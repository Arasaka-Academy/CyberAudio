# 固定短音频的补零位置对照

把不足一秒录音的补零从结尾移到开头，没有修复已知的 0.6 秒 `thank you` 空转写。七个固定样本共完成 **21 次**原生 HTTP 请求；原始音频和显式尾部补零两组均逐项复现旧基线。头部补零让一个混说控制的编辑数减少一，总编辑数 **11／11／10**，但已知问题仍为空，未通过预定资格条件。本次试验已结束，没有扩大样本、搜索其他长度或改变默认预处理。

## 协议与对照

[协议](protocol.json)在加载模型前冻结，源码基线为 `main@22b55e3`。使用上一阶段已验收的独立 App 内置 Service，构建源码为 `b06dc7b`，没有替换或重启正式 App。相同模型、auto 语言、空上下文、greedy／temperature 0、max 1024、原始 PCM 样本值及顺序均不变。

先前只读检查确认 SDK `splitAudioIntoChunks` 对不足一秒的输入在**结尾**补零至 16,000 帧；`generateManaged` 在特征提取之前调用该函数。已知录音有 9,600 帧，原路径因此追加 6,400 个零。端点不是精确零，不能据此证明录音裁切或空输出原因。本轮只改变相同零样本的位置，不增加有效音频、不提高音量，也不添加答案提示。

从原完整 1,315 条 ASCEND test split 按真实 PCM 帧数筛出 **362 条不足一秒**的录音：271 中文、87 英文、4 混说。排除已知问题后，各语言按 ID 字典序取首、末记录，获得六个控制，不参考新输出、音量或答案。此前电平分析中的“79 条不足一秒”属于 RMS 不高于 −30dBFS 的子集，和这里的全量短音频计数口径不同。

执行顺序和前置条件为：

1. 七条原始 WAV，各执行一次；要求 `text`、`language`、`no_speech`、模型及固定版本逐项等于保留的自然基线。
2. 同七条音频显式在结尾补零至 16,000 帧，各执行一次；再次要求以上字段全部相同。
3. 只有前两组 14 项匹配后，才执行七条显式在开头补零至 16,000 帧的输入。

每个调用的输入时长单独核对；原始文件时长与补零文件不同，不能要求整个 HTTP 响应相等。三组进入模型的有效波形长度均为 16,000 帧，这是原拆分源码和尾部控制共同支持的结论，没有另做内部张量采集。所有调用在一个离线沙箱原生实例上顺序完成，零重试、零跳过。

预定资格要求是已知问题按冻结作者分词后精确匹配参考 `thank you`，六个控制逐条编辑数均不增加且不新增空输出。即使符合，也只允许另立独立协议进一步评估；本次结果没有达到该条件。

## 结果和文件核验

| 组别 | 调用数 | 旧基线文本／语言／模型匹配 | 总混合编辑数 | 已知 `thank you` |
|---|---:|---:|---:|---|
| 原始 WAV，SDK 尾部补零 | 7 | 7／7 | 11 | 空 |
| 显式尾部补零 | 7 | 7／7 | 11 | 空 |
| 显式头部补零 | 7 | 不作为旧基线匹配条件 | 10 | 空 |

头部组相对原始组一条改善、六条编辑数相同、零条增加；没有新增空控制。六个控制的逐条计数及已知问题的三组原值见[摘要](summary.json)，控制完整转写保持私有。已知问题三组均为 `no_speech=false`，其含义继续是“不是精确数字静音”，不能当作通用 VAD 或人耳语音判定。

[输入核验](transform-verification.json)逐项确认 21 个输入的 PCM 与 FFmpeg 解码结果逐字节相同。头部／尾部组完整保留原始 PCM，只交换零填充的位置；原文件没有改写。[独立分析程序](analyze.py)重新检查 WAV／PCM 摘要、元数据选样、两组 14 项基线匹配，用另一个完整矩阵算法复算全部 21 个编辑距离，并核对冻结评分器的结果。

[运行回执](inference.json)记录 21 次成功请求和 EOF exit 0，整体约 15.20 秒；该范围包含启动／校验／预热／HTTP，不是物理麦克风性能或跨实现速度比较。分析同时核验 102 个跟踪源文件的内容、1,026 个受保护文件的大小／mtime、六个冻结 App／DMG 文件摘要和七个当前 App 文件摘要。生产实例、配置和 Token 保留；所属 Helper 已退出，18902 端口关闭，请求临时目录为空。
