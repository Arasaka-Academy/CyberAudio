# CyberAudio 项目进展与全量代码审查

日期：2026-11-06，续审至 2026-11-07。审查基线：`main@96210dd`；修复分支：`codex/robustness`。

CyberAudio 已具备完整主链路，但本轮实际验收尚未达到稳定分发标准。原审查的 1 项 P1、4 项 P2，以及后续发现的 7 项 P2 均已修复，累计 12 项；最新补全 SDK 异常加载时的模型文件保护。首次启动、可恢复下载、日常 CI 和证书签名流程已实现，固定 100 条真人录音和 M4／16GiB 完整服务回归也已补齐。两次 M4 两小时负载分别在 707／1229 个完成周期后失败，第二次终态明确为短句 TTS `generation_limit`；固定种子也已复现。后续采样候选的完整配对仍有日期／人名等回退，未调整默认参数；另修复了两种方言音色覆盖显式英文的问题。中英拼接仍有遗漏／翻译，公网完整下载也未通过。这些问题以及真实桌面、Developer ID 公证和升级权限验收仍待解决。

“功能已实现”“自动回归通过”“实际模型成功”“用户体验验收”和“正式交付”分别记录。当前源码使用 MLX Swift／Metal；Core ML／ANE 仍为实验，未形成性能或能耗收益结论。

## 审查范围和方法

顺序检查 App 的音频、进程、听写、文本插入、设置与更新生命周期；原生 HTTP、并发协调、音频解码、资产和 Qwen 适配；构建、签名、发布工作流、回归入口；并检查遗留 Python 与 Core ML／Qwen 实验代码同当前交付的边界。第三方代码按固定版本、锁文件和受校验的补丁检查，未对所有上游项目逐行审计。

对可复现问题补回归，先观察失败，再验证修复。生产代码之外，同时审查测试是否使用新构建、真实网络行为是否被替身掩盖，以及报告是否超出实际验证范围。收尾复查重点为取消后的任务所有权、下载文件保护、更新等待和分发失败时的阻止路径。

### R1 · P1 · 旧播放回调覆盖新播放状态 — 已修复

流式音频生成完成后立即重播，停止旧 AVAudioPlayerNode 触发的完成回调会把新播放的 `playing` 清为 false。初次探针观察到实际 AVAudioPlayer 仍在播放，更新门闩却已允许安装。

[AudioWorkspace.swift](../../Sources/CyberAudio/AudioWorkspace.swift) 为播放增加会话标识，停止前先作废旧会话；节点完成回调检查会话，播放器 delegate 检查对象归属。真实 AVFoundation／原生 HTTP 集成回归覆盖重播、停止、迟到回调、更新等待和恢复。

### R2 · P2 · 未读 WAV 响应可无限阻塞更新 — 已修复

原实现排入响应结束标志时即取消 timeout；客户端保持连接却不读较大的 WAV，发送未完成，更新排空记录持续存在。初次探针在 0.1 秒超时配置下，1 秒后仍观测到阻塞。

[HTTPService.swift](../../Native/Sources/CyberAudioCore/HTTPService.swift) 将截止时间保留至最终 flush 完成。超时处理可关闭已排入响应结束的连接，断连清理保持幂等；生产者继续计算时仍保留推理槽。真实 TCP 回归验证客户端无需主动断开，截止时间到达后即可结束响应排空。

### R3 · P2 · ASR 取消等待整段推理完成 — 已修复

固定版本 SDK 的同步 ASR 生成内部没有取消检查，App／HTTP 的取消仅在完整调用前后生效，共用模型槽可能长期被占用。

[SDK 适配脚本](../../scripts/patch_mlx_audio.swift) 为编码、预填充、token 与分段边界增加取消检查，返回前等待已排入的 GPU 工作。原非抛出 SDK 入口保留原契约，补丁先验证原始源码 SHA，并验证重复执行和篡改拒绝。[QwenEngine](../../Native/Sources/CyberAudioInference/QwenEngine.swift) 调用受管理的同步入口。

真实本地 ASR 验证预先取消、生成中取消及同一模型恢复。记录中的 694ms 是注入取消前经过的时间，不能解释为取消延迟；单次 Metal 调用仍可能无法立即打断。

### R4 · P2 · 音频集成测试可能复用旧二进制 — 已修复

[test_audio_workflow.sh](../../scripts/test_audio_workflow.sh) 每次先增量构建 `CyberAudioFixture`，再运行集成测试。服务源码变化现在由构建系统判定重编译，文件存在不会跳过构建。

### R5 · P2 · 现役发布工具测试未进入必跑检查 — 已修复

[Makefile](../../Makefile)、[test_tools.sh](../../scripts/test_tools.sh)、`pyproject.toml` 和 `uv.lock` 将现役发布、资产、语料和 SDK 适配测试纳入 `make check`。锁定的 Python 工具环境位于 `.context/tool-tests-venv`，原 `.venv` 与历史服务保留。

[Checks 工作流](../../.github/workflows/check.yml) 对 PR／main 配置同一入口，并编译真实推理 Helper；发布工作流复用检查。发布凭据仅在受信任的 Release 作业中使用。

### R6 · P2 · 符号链接模型根目录校验成功但加载失败 — 已修复

实际服务验收中，模型文件 SHA 校验通过，SDK 枚举符号链接目录时却返回 Cocoa 256／POSIX 20（Not a directory）。这导致合法模型配置无法启动。

`QwenEngine.load` 在传给 SDK 前规范化 ASR／TTS 根目录。使用符号链接根目录的实际双模型加载、预热和完整服务验收随后通过；该路径保留在显式的真实模型验收驱动中。

### R7 · P2 · 复用 App 的分发打包绕过公证票据检查 — 已修复

新增签名流程的收尾审查发现：`build_dmg.sh --reuse-app` 虽复查 Developer ID、团队和强化运行时，却未要求已有 App 的 staple 票据及 Gatekeeper 接受。

[sign_app.py](../../scripts/sign_app.py) 的分发验证默认强制 `stapler validate` 和 Gatekeeper 评估；仅签名与提交公证之前的内部阶段允许暂不检查票据。失败回归分别模拟缺少票据和 Gatekeeper 拒绝，两项先失败后通过。没有证书时的替身验证不能代替实际 Apple 公证。

### R8 · P2 · 输出设备变化后播放状态无法恢复 — 已修复

后续检查设备恢复路径发现，PCM 播放没有订阅 `AVAudioEngineConfigurationChange`。输出配置变化使系统停止引擎时，`playing` 仍可保持 true，未完成的生成继续收取数据，更新门闩也无法等到播放结束。真实 AVFoundation 引擎停止后主动发送该通知的回归，修复前确认失败。

[AudioWorkspace.swift](../../Sources/CyberAudio/AudioWorkspace.swift) 持有当前引擎的通知观察者，异步转到主 actor 并检查对象归属；停止时先注销观察者。当前引擎中断会取消未完成的生成，等待 HTTP 排空后释放更新，保留已经完成的 WAV，并提示检查输出设备后重试。播放器解码失败和失败完成回调同样释放播放归属、保留成品；成功重播只清理先前的语音生成错误，不清理识别错误。

集成回归覆盖生成中／完成后中断、旧引擎迟到通知、旧播放器错误、失败完成、重播和实际服务更新租约恢复。使用真实 AVFoundation 与原生 HTTP 测试服务，配置通知由测试主动发送；这不等于实际拔插、蓝牙切换、睡眠或人耳试听通过。续审证据单独保存在 [playback-recovery](../evidence/robustness-2026-11-06/playback-recovery/README.md)，此前的构建、源码快照及 DMG 回执仍对应 R1–R7 阶段，不覆盖新字节。

后续完整检查暴露另一种事件顺序：引擎停止触发的末尾完成回调先清理归属，配置通知随后到达，导致设备中断提示丢失。`939050f` 在末尾回调检查引擎是否仍运行，复用当前设备中断路径并保留完整 WAV。确定性回归先以 exit 133 失败，再通过；[追加证据](../evidence/robustness-2026-11-06/retry-and-matrix/README.md)保留红绿断言和最新完整检查。

### R9 · P2 · 持续负载失败丢失请求原因 — 已修复

首次 M4 长时验收在请求失败后退出，但驱动只报告“Soak request did not complete”，没有保存请求 JSON／错误码和当前负载；整体 native 报告停留在部分结果，给后续归因造成信息缺口。

[verify_native.swift](../../scripts/verify_native.swift) 现在保存失败请求、查询 HTTP 状态、周期／语料／音色／格式、失败原因和结束时间；整体报告异常退出时明确 failed。新增实际 Swift HTTP 回归在修复前因缺失 `failed_request` 失败，修复后通过；现役工具回归 37 项全部通过、没有跳过。未改变推理源码、模型参数或严格验收条件。

后续复查补全同一问题的提前抛错路径：WAV 422 错误响应和 PCM 传输中断原先也会跳过终态查询。`83f0ec3` 保存错误响应／传输错误，并在需要时有界查询请求终态。两条真实 HTTP 回归均先失败后通过；最新目标回归 10 项、全部现役工具 39 项通过且无跳过，见 [reporting-transport](../evidence/robustness-2026-11-06/reporting-transport/README.md)。M4 重测全程使用其原诊断驱动，现已失败终止，没有为工具更新重启。

### R10 · P2 · 单次暂时网络故障终止整个下载 — 已修复

实际公网续传反复失败后，受控真实 HTTP 回归确认：一个分段的暂时断连或 HTTP 503 会直接终止整次下载，无法自动恢复。`565eb1c` 只重试尚未提交的相同 Range，最多两次；暂时网络错误及 408／429／500／502／503／504 使用可取消退避，并遵守最多 30 秒的数字／日期 `Retry-After`。更长的服务等待返回可恢复错误，永久 HTTP／TLS／范围／摘要错误不重试。

新增回归先观察到五个断言／错误，再通过。原最终文件、持久分段和校验规则保留；错误信息仅显示安全网络类别，不泄露 URLSession 原始描述或重定向地址。最新完整检查包含 33 项原生契约；新实际 Assets 候选在 M4 有界运行后也以连接中断失败。受控恢复通过不等于完整公网下载通过，见[追加证据](../evidence/robustness-2026-11-06/retry-and-matrix/README.md)。

同一路径的 8MiB Range 未完成、1MiB curl／URLSession 均完整成功且 SHA 一致后，`f42bafe` 增加一次小分段降级：大分段耗尽超时／连接中断重试后，当前资产剩余部分改用 1MiB；不改已有前缀，小分段仍最多重试两次，HTTP／TLS／校验错误不降级。三个真实 HTTP 回归先出现两个预期失败，再通过；最新完整检查为 **36／39／14**。该最终 App 的完整真实模型验收也通过；M4 的同一签名 Assets 随后在 TLS 阶段失败，完整公网门槛仍未通过，见[最终阶段证据](../evidence/robustness-2026-11-06/adaptive-ranges/README.md)。

### R11 · P2 · 方言音色覆盖显式英文 — 已修复

SDK 在 eric／dylan 查到方言配置后，无条件替换语言 ID，显式英文也被改成四川／北京方言。Qwen 参考实现只对中文／自动语言应用该覆盖。固定输入 `1234`、种子 31 的实际模型对照中，同一音色的英文／中文请求得到完全相同的 token 和 PCM，两个行为检查均先失败。

`5479313` 的[受校验 SDK 适配](../../scripts/patch_mlx_audio.swift)将覆盖限制为中文／自动；采样参数保持原值。通过真正的生产 `generateManaged` 入口重跑后，两种音色的英文输出均变化，中文方言 token／PCM 与原基线逐字节一致。适配器只允许已知旧版本摘要平滑升级或当前精确补丁，继续拒绝不明源码修改；实际命令的升级回归先失败，再与重复执行／篡改拒绝一起通过。完整检查为 **36／40／14**。边界对照不代替完整语言能力和人耳验收。

八个修复前后输出进一步经最终 App 的 ASR 自动检测：旧英文请求均回读为中文，修复后两个英文请求仍被检测为 Hindi／中文，未确认正确英文；中文请求保持原结果。WAV 有效帧与原 PCM 摘要复核一致。不能仅凭 ASR 判定实际发音语言，也不能将路由修复算作英文数字质量通过；完整回读、红绿结果和最终包证据见 [language-routing](../evidence/robustness-2026-11-06/language-routing/README.md)。

### R12 · P2 · SDK 异常加载可能删除整个模型目录 — 已修复

固定 SDK 把普通文件形式的 `speech_tokenizer` 当作损坏缓存，调用 `removeItem(at: modelDir)`，再抛出加载错误。CyberAudio 的 23 文件校验通常会先拒绝这种异常，本风险依赖校验后目录发生变化；本轮没有观察到正式模型损失。

### 实际边界和受控质量的追加验收

[边界与质量证据](../evidence/robustness-2026-11-06/quality-boundaries/README.md) 使用同一最终 Helper，在 M1 独立目录执行。实际活动 ASR／非流式 TTS 断连后约 299／364ms 空闲，后续同实例请求成功；该次时间不是取消延迟保证。60 秒输入接受，60.1 秒返回 413；417 scalar 英文生成完整 31.68 秒 WAV，500 scalar 中文明确返回 422 `generation_limit`，没有把截断 WAV 计作成功。内容回读没有替代人耳试听。

另用八条固定真人专名／数字输入构造 24 个单语条件、四个中英拼接和两个控制。同一 M1 的旧、新 Helper **30／30 输出相同**，24 条单语按现有评分器不回退。最初私有生成器把 IEEE float32 WAV 当作整数，波形检查发现后排除旧结果；修正后逐样本复核 FFmpeg 解码、量化误差、SNR 和音频摘要，原始失败记录保留。

四个拼接输入均只输出其中一种语言，遗漏整段另一种语言。它们是不同录音的受控拼接，尚未证明自然混说质量，也未确定遗漏的模型／集成归因；需要作为下一步质量工作处理。小样本 CER／WER 没有数字语义等价或实体标注，不能当作专名准确率；纯噪声和静音控制为空也不能证明通用 VAD。

继续用相同源录音统一每段 RMS，并交换先后顺序形成八个对照。部分输入恢复两段，另一些仍有整段遗漏，或把中文翻译成英文；音量差异不足以解释所有现象。当前只完成候选 Helper 的诊断，未将这些拼接当作自然混说验收，也未据此调整默认模型参数。

上述八个输入追加 auto／zh／en 对照共 24 次实际 ASR：强制中文在两组英文在前的 clean 输入上恢复原中文，但在桥梁中文在前的条件中只保留中文，仍遗漏英文。固定选择某一种语言不能解决所有完整性问题；自然混说、提示／分段策略和模型能力仍需按原质量门槛评估。
